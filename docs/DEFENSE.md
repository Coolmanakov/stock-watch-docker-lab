# Сценарий защиты: 5–7 минут

## Что объяснить в начале

«Я сделал Stock Watch — приложение контроля складских запасов, тема №55. Пользователь видит товары, может менять их остаток и запускать проверку. Сервис расчёта определяет критический порог и рекомендуемый заказ. Приложение состоит из четырёх контейнеров: frontend, backend, PostgreSQL и web-service».

## Порядок показа

### 1. Код и запуск

Покажи дерево проекта, `docker-compose.yml`, Dockerfile и `db/init.sql`. Обрати внимание на четыре сервиса, сеть `bridge`, `depends_on`, `healthcheck`, volume и опубликованный порт frontend.

Из папки проекта:

```bash
docker compose up --build -d --wait
docker compose ps
```

Покажи четыре `healthy`. Объясни: «Compose собирает три собственных образа, использует готовый PostgreSQL и запускает все сервисы в одной сети. Backend стартует после готовности базы и вычислительного сервиса».

### 2. Чтение базы

Открой http://localhost:8080, нажми «Загрузить склад».

«Эта кнопка вызывает GET /api/products. Backend читает товары из PostgreSQL. Первые три товара добавились автоматически из init.sql при первом запуске».

Если в БД уже есть изменения после тренировочного запуска, количество и значения могут отличаться. Для показа формулы создай отдельный товар с параметрами ниже.

### 3. Вычислительный сервис

Нажми «Проверить запасы».

«Backend отправляет снимок товаров отдельному web-service по HTTP. Порог равен расходу в день, умноженному на дни доставки, плюс страховой запас. Backend сохраняет результат в таблицу analyses».

На исходном USB-C кабеле: остаток 12, расход 5, доставка 3 дня, резерв 5. Порог = 20. Остаток меньше порога. Рекомендуемый заказ — 43 штуки: 20 + 5 × 7 − 12.

### 4. CRUD

Добавь товар «Кабель для защиты» с остатком 12, расходом 5, доставкой 3 и резервом 5. Запусти проверку: порог 20, статус «Ниже порога».

Нажми «Изменить» у своего товара, поставь остаток 80, сохрани, повтори проверку. Теперь статус «Достаточно», заказ 0.

«Создание — POST, чтение — GET, изменение — PUT, удаление — DELETE. Все операции выполняет backend через PostgreSQL».

### 5. Подтверждение хранения

Нажми «Загрузить историю». Покажи, что предыдущая проверка сохранила остаток 12, а новая — 80.

В терминале можно показать настоящие строки базы:

```bash
docker compose exec db psql -U lab -d stockwatch -c 'SELECT id, name, quantity FROM products ORDER BY id;'
docker compose exec db psql -U lab -d stockwatch -c 'SELECT id, created_at FROM analyses ORDER BY id DESC LIMIT 5;'
```

### 6. Сохранность после пересоздания

Запомни ID товара, остаток 80 и ID последней проверки. Затем:

```bash
docker compose down
docker compose up -d --wait
```

Обнови страницу, нажми «Загрузить склад» и «Загрузить историю». Убедись, что значения и записи сохранились.

«Контейнеры удалились и были созданы заново. Данные остались, потому что хранятся в именованном volume. Обычный down volume не удаляет».

После показа можешь удалить свой тестовый товар через кнопку. Снимки в истории останутся.

## Дополнительный показ отказа сервиса

Если преподаватель попросит показать независимость компонентов:

```bash
docker compose stop web-service
```

«Загрузить склад» продолжит работать. «Проверить запасы» покажет ошибку. Новая проверка не сохранится. Затем восстанови сервис:

```bash
docker compose start web-service
```

Дождись `healthy` в `docker compose ps`, повтори проверку. Не оставляй сервис выключенным перед основной демонстрацией.

## Короткие ответы на вопросы

| Вопрос | Ответ |
| --- | --- |
| Что такое образ? | Шаблон файловой системы и команды запуска, из которого создаётся контейнер. |
| Что такое контейнер? | Изолированный запущенный экземпляр образа. На Mac Linux-контейнеры работают в среде Docker Desktop. |
| Зачем Compose? | Описывает все сервисы в одном YAML и управляет их совместной сборкой и запуском. |
| Почему четыре контейнера? | У каждого своя задача: интерфейс, API, данные и расчёт. Это также требование задания. |
| Почему расчёт вынесен отдельно? | Его можно менять и запускать независимо; он не знает о PostgreSQL и не хранит состояние. |
| Как контейнеры находят друг друга? | Через имена сервисов в сети Compose: db, backend, web-service. |
| Почему не localhost внутри backend? | localhost обозначает сам контейнер backend, а база находится в другом контейнере — db. |
| Зачем healthcheck? | Проверяет, что сервис готов принимать запросы. Для БД используется pg_isready, backend проверяет доступ к таблицам. |
| Зачем depends_on? | Задаёт зависимости запуска. С service_healthy ждёт успешного healthcheck; не исправляет любой последующий сбой автоматически. |
| Зачем volume? | Хранит данные отдельно от жизненного цикла контейнера. |
| Почему нет внешнего API? | Задание разрешает локальный микросервис. Наш сервис реально рассчитывает результат из переданных данных. |
| Где первичные данные? | В db/init.sql, который PostgreSQL выполняет при создании пустой БД. |
| Есть ли CRUD? | Да: создание, список, изменение и удаление товара через REST API. |
| Как защищены SQL-запросы? | Значения передаются параметрами psycopg, без склеивания пользовательского текста с SQL. |
| Какие ограничения модели? | Постоянный расход, фиксированный срок доставки, нет авторизации и реального учёта поставок. Это локальный учебный проект. |
